## 需求背景

前一阶段平台端 Demo 主要围绕「场景库、数据集、模型」三个概念展开。这个结构能够解释官方场景模板下的训练流程，但对另一条真实业务路径支持不足：用户可能先在客户端通过 DIY 检测工具采图、上传数据、在平台训练出一个能力，再把这个能力下发到客户端使用。

如果平台要求用户必须先选择场景模板，或者要求所有训练能力都必须挂在某个场景下，会让“从零启动一个新检测能力”的路径变重。相反，如果只保留模型和数据集，又难以表达一个可独立训练、独立下发、持续积累现场数据的完整检测能力。

因此需要引入「算子实例」作为平台端新的核心业务实体。场景实例不再直接管理模型或数据集，而是在算子实例基础上组织完整检测流程。

## 设计目标

1. 定义「算子实例」作为平台端可独立训练、独立下发、独立积累数据的核心业务实体。
2. 同时支持“客户端 DIY 从零启动能力”和“平台场景模板搭建完整方案”两条业务路径。
3. 明确算子实例、场景模板、场景实例、公共数据、客户端检测工具之间的边界。
4. 明确独立算子加入场景时采用“归入”语义，而不是默认复制。
5. 保留客户端离线运行所需的不可变部署描述，但第一版不强制引入独立“算子快照”实体。
6. 重新解释旧图像库能力，避免公共数据、图像池、数据集、典型样本之间概念混乱。

## 设计结论

### 1. 平台核心从“模型”升级为“算子实例”

算子实例是平台端新的核心业务实体。它代表一个可被训练、可被下发、可持续积累数据的检测能力。

算子实例具备以下特征：

1. 可以独立于场景存在。
2. 可以独立训练。
3. 可以独立下发给客户端。
4. 可以持续积累客户端回流数据。
5. 可以由公共数据训练产生。
6. 可以加入一个场景实例，参与完整检测流程。
7. 可以包含多套训练权重。
8. 可以拥有典型样本。
9. 可以被客户端单独拉取。

算子实例不是“模型”的简单改名。原来的模型更接近算子实例下的“权重版本”或“训练结果”。

推荐结构：

```text
算子实例
  ├─ 基础信息
  │   ├─ 算子名称
  │   ├─ 算子类别
  │   ├─ 输入输出契约
  │   └─ 运行参数
  ├─ 算子数据
  │   ├─ 普通样本关系
  │   └─ 典型样本关系
  ├─ 训练数据版本
  │   ├─ 样本集合
  │   ├─ 标注快照
  │   └─ 数据划分
  ├─ 权重版本
  │   ├─ 权重 ID
  │   ├─ 训练来源
  │   ├─ 指标
  │   └─ 文件地址/哈希
  └─ 当前下发配置
```

### 2. 场景实例是在算子实例基础上组织的流程

场景实例不是训练主体。场景实例的核心价值是组织多个算子实例及其连接关系，并形成一个可被客户端下载的完整检测流程。

推荐结构：

```text
场景实例
  ├─ 场景名称
  ├─ 来源场景模板
  ├─ 算子实例列表
  ├─ 算子连接关系
  ├─ 输入输出映射
  ├─ 流程校验状态
  ├─ 平台预推理结果
  └─ 可分发配置
```

场景实例具有分发作用，但它不是场景模板。

### 3. 场景模板是官方脚手架

场景模板是官方提供的创建脚手架，不拥有用户真实数据和真实算子实例。

场景模板描述：

1. 适用工业检测问题。
2. 推荐需要几个算子。
3. 每个算子的类别。
4. 算子之间如何连接。
5. 需要什么输入输出。
6. 推荐的采图、标注、训练和验证流程。

场景模板的作用是降低用户理解成本，而不是替代算子库。

### 4. 客户端检测工具是现场本地运行配置

客户端检测工具是客户端在具体现场形成的本地运行配置。它可以来自：

1. 单独拉取一个算子实例。
2. 拉取一个完整场景实例。

客户端检测工具不等于平台场景实例，也不等于场景模板。

```text
平台算子实例
  -> 客户端单算子检测步骤

平台场景实例
  -> 客户端完整检测工具
```

## 公共数据与旧图像库的关系

公共数据不完全等同于之前的图像库。

更准确地说：旧图像库是公共数据能力的前身，但新架构下需要拆分成「图像资产」和「归属关系」两个层次。

### 旧图像库的问题

旧图像库更像文件夹式图片管理：

1. 用户上传图片。
2. 图片放在某个文件夹。
3. 用户自行理解这些图片未来用于哪个训练任务。
4. 数据和模型、场景、客户端工具之间关系较弱。

这种方式灵活，但容易散。用户需要靠命名、经验和手工维护理解数据用途。

### 新架构下的公共数据

公共数据是“尚未归属到任何算子实例的图像资产集合”。

它主要承接：

1. 客户端 DIY 检测工具上传的图片。
2. 检测记录中被用户标记上传的图片。
3. 本地批量上传但暂未选择算子的图片。
4. 历史迁移中尚未归属到算子的图片。

公共数据的作用是暂存、筛选、选择和转入算子训练。

```text
公共数据
  -> 选择图片
  -> 标注 / 训练
  -> 创建独立算子实例
```

### 图像资产只保存一次

无论图片来自公共数据、算子数据还是典型样本，物理图像文件都只保存一次。

不同业务对象通过关系引用同一个图像资产：

```text
图像资产
  ├─ 公共数据关系
  ├─ 算子 A 普通样本关系
  ├─ 算子 A 典型样本关系
  └─ 算子 B 典型样本关系
```

### 公共数据与算子数据的区别

| 概念 | 定义 | 是否归属算子 | 主要用途 |
| --- | --- | --- | --- |
| 图像资产 | 物理图片及基础元数据 | 否 | 文件保存、预览、来源追踪 |
| 公共数据 | 未归属算子的图像资产集合 | 否 | 从零训练新能力的候选数据 |
| 算子数据 | 某个算子实例引用的图像资产集合 | 是 | 持续训练、回流、样本管理 |
| 典型样本 | 算子—图片关系上的标记 | 是 | 示例、复制、模板化、少样本启动 |
| 训练数据版本 | 从算子数据中冻结出的样本和标注快照 | 是 | 训练追溯、权重版本来源 |

### 旧图像库如何迁移

旧图像库能力不应直接废弃，而是拆成两部分：

1. 未归属图片进入「公共数据」。
2. 已经明确服务某个检测能力的图片，进入对应「算子数据」。

因此，公共数据不是“旧图像库改名”，而是旧图像库在新架构下的一种未归属状态。

## 标注数据归属与预标注

### 标注不直接归属于图像资产

标注数据不应直接归属于图像资产本身。

原因是同一张物理图片在不同算子实例中可能承担完全不同的训练含义。

例如同一张齿轮原图：

1. 在齿面定位算子中，标注对象是齿面区域。
2. 在气泡检测算子中，标注对象是气泡、划痕等缺陷。
3. 在图像分类算子中，标注对象可能是 OK / NG 分类。
4. 在 OCR 算子中，标注对象可能是字符区域和识别文本。

如果把正式标注直接挂在图像资产上，会导致不同算子的标注互相污染，也无法解释同一张图被多个训练能力复用的情况。

### 标注归属于算子—图像关系

正式标注应归属于「算子图像关系」，也就是某张图在某个算子实例语境下的样本关系。

推荐结构：

```text
ImageAsset
  只保存图片文件和基础元数据

OperatorImageRelation
  表示某张图片属于某个算子实例
  正式标注、预标注、标注状态挂在这里

OperatorTrainingDatasetVersion
  冻结一批 OperatorImageRelation 及其标注快照
```

示例：

```text
图像资产 gear_001.jpg
  ├─ 齿面定位算子：齿面框 1 个，已确认
  ├─ 气泡检测算子：气泡 3 个、划痕 1 个，已预标注
  └─ OK/NG 分类算子：NG，已确认
```

### 算子图像关系字段建议

```text
OperatorImageRelation
  ├─ relation_id
  ├─ operator_id
  ├─ image_asset_id
  ├─ sample_role: 普通样本 / 典型样本
  ├─ source_type: 公共数据转入 / 客户端回流 / 手动上传 / 场景复制
  ├─ annotation_status: 未标注 / 已预标注 / 已确认
  ├─ annotation_content
  ├─ pre_annotation_content
  ├─ pre_annotation_source
  ├─ pre_annotation_weight_id
  ├─ reviewed_at
  └─ updated_at
```

### 标注内容与算子类别相关

标注内容不是固定一种格式，而是由算子类别决定。

| 算子类别 | 正式标注内容 |
| --- | --- |
| 目标检测 | 矩形框、类别、可选属性 |
| 目标检测 OBB | 旋转框、类别、角度 |
| 图像分类 | 图片级类别 |
| OCR | 文本区域、识别文本、可选字符级框 |
| 尺寸/几何测量 | 点、线、圆、距离、角度等构造元素 |

Demo 首版可以先覆盖目标检测和图像分类，其他类型保留结构入口。

### 训练数据版本保存标注快照

训练数据版本不是继续编辑标注的地方，而是冻结快照。

```text
算子数据
  -> 选择样本
  -> 完成标注
  -> 创建训练数据版本
  -> 冻结样本集合、标注内容、数据划分
  -> 训练生成权重版本
```

发布后的训练数据版本不能直接修改。后续调整应回到算子数据中修改标注，再创建新的训练数据版本。

### 如何查看图像标注信息

需要提供两个入口。

#### 入口一：算子详情中的算子数据

这是标注查看和编辑的主入口。

在算子详情页的「算子数据」中，每张图展示：

1. 缩略图。
2. 来源。
3. 是否典型样本。
4. 标注状态。
5. 预标注数量。
6. 正式标注数量。
7. 类别统计。
8. 最近更新时间。

点击图片进入标注工作区，看到该算子语境下的标注内容。

#### 入口二：图像资产详情

这是全局索引入口。

图像资产详情页不直接编辑标注，而是展示这张图被哪些算子使用：

```text
图像：backplate_upper_001.jpg

关联算子标注：
1. 背板外观缺陷检测算子
   状态：已确认
   标注：划伤 2，脏污 1

2. 背板 OK/NG 分类算子
   状态：已预标注
   标注：NG
```

用户点击某条关系后，进入对应算子的标注工作区。

### 客户端检测结果回流为预标注

客户端检测结果回流到平台时，不应直接成为正式标注，而应先成为预标注。

推荐流程：

```text
客户端检测结果回流
  ↓
平台解析 operator_id / 权重 ID / 配置修订号
  ↓
图片资产入库或复用已有图片
  ↓
建立或更新 OperatorImageRelation
  ↓
检测结果保存为 pre_annotation_content
  ↓
标注状态变为“已预标注”
  ↓
用户进入算子标注工作区
  ↓
应用、调整或删除预标注
  ↓
确认后写入 annotation_content
  ↓
标注状态变为“已确认”
```

核心原则：

```text
客户端推理结果 ≠ 正式标注
客户端推理结果 = 预标注建议
用户确认后的内容 = 正式标注
```

### 客户端实例与平台算子的回流边界

客户端每个图像处理实例或图像检测实例都拥有一个本地算子槽位，但创建时可以尚未关联平台算子。

1. 未关联平台算子时，实例可以运行并保留输入，但不产生可归属的平台算子推理输出。
2. 未关联实例的输入只能由用户手动回流到平台图像库，平台不自动猜测算子归属。
3. 用户在客户端为实例选择平台算子后，客户端保存 `operatorId`、`weightId`、`deploymentId` 和 `configRevision`。
4. 后续回流数据按 `operatorId` 直接进入对应算子的样本池。
5. 平台算子不存在或已被删除时，回流任务失败并保留，不降级进入图像库。
6. 图像处理算子的输入是原始图像；图像检测算子的输入是实际消费的处理后子图或全图处理结果。
7. 检测算子回流处理后子图时不额外携带原始整图。

```text
未关联客户端实例
  -> 用户手动回流输入
  -> 平台图像库

已关联客户端实例
  -> operatorId + 实际输入 + 推理输出
  -> 平台算子样本池
  -> 待标注 / 待确认预标注
```

### 预标注来源

预标注来源可以包括：

1. 客户端检测结果回流。
2. 平台已有权重版本推理。
3. 相似样本标注复用。
4. 固定区域模板。
5. 人工 ROI 快速生成。

首版 Demo 不需要把所有来源都做复杂，只需要明确入口和状态：

1. 回流结果。
2. 选择已有权重进行预标注。
3. 手动调整后确认。

### 预标注操作

标注工作区需要支持：

1. 查看预标注框或预标注类别。
2. 一键应用全部预标注。
3. 单个应用。
4. 删除误检。
5. 调整框位置或类别。
6. 确认为正式标注。
7. 完成并下一张。

一旦确认，预标注内容写入正式标注字段。预标注本身可以保留来源记录，用于追溯，但训练只使用正式标注。

## 两条常见业务流程

### 流程一：从零启动一个新能力

适用于平台暂未支持对应场景模板，用户先在客户端现场试起来。

```text

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

```

这条路径不要求平台必须先有场景，也不要求客户端必须从场景开始。

### 流程二：平台先构建完整方案

适用于官方场景模板已经覆盖用户需求，用户希望快速搭建端到端检测流程。

```text

  ↓

  ↓

  ↓

  ↓

  ↓
多个客户端主动拉取该场景
  ↓
分别形成可以离线运行的检测工具
```

这条路径的重点是完整流程组织和分发。

## 算子实例归属规则

### 采用“归入”语义

当公共数据训练出了独立算子实例 O1，用户创建场景 A 时选择 O1，采用“归入”语义：

```text
独立算子实例 O1
  ↓ 加入场景 A
场景 A 引用 O1，O1 身份不变
```

规则：

1. O1 原本独立存在。
2. O1 加入场景 A 后，身份不变。
3. O1 的数据、典型样本、权重版本全部保留。
4. O1 最多归入一个场景实例。
5. 已归入场景的算子仍然可以被客户端单独拉取。
6. 如果另一个场景也想使用同样能力，必须显式复制算子，产生新的算子实例。
7. 场景复制时，也复制出新的算子实例。

### 为什么不默认复制

默认复制会造成几个问题：

1. 用户以为选择的是同一个能力，实际平台产生了另一个算子。
2. 已积累的回流数据和典型样本容易被切断。
3. 客户端继续拉取哪个能力变得不直观。
4. 算子历史和训练追溯复杂化。

因此，加入场景默认不改变算子身份。

### 什么时候需要复制算子

以下情况需要显式复制：

1. 一个算子能力要被另一个场景使用。
2. 用户复制整个场景实例。
3. 用户希望基于已有算子做不同方向的训练实验。
4. 用户希望保留原算子稳定运行，同时派生一个新能力继续调整。

复制算子时：

1. 复制算子配置。
2. 复制当前权重或指定权重。
3. 复制典型样本关系。
4. 不复制普通日常数据关系。
5. 物理图片继续共享。
6. 新算子的典型样本标记独立，后续互不影响。

## 典型样本规则

典型样本是算子数据关系上的标记，不复制物理图片。

```text
图像资产 X
  ├─ 算子 O1：典型样本
  └─ 算子 O2：普通样本
```

场景复制或算子复制时，“复制典型样本”的含义是：

1. 复制典型样本关系。
2. 不复制普通算子—图片关系。
3. 不复制物理图片文件。
4. 新算子的典型样本标记独立。

这样既能保留样板能力，又不会把大量日常回流数据一并带走。

## 部署描述与算子快照

客户端需要离线运行，因此不可变部署内容仍然有价值。

第一版不强制增加独立“算子快照表”，可以先体现为拉取接口返回的部署描述。

建议部署描述包含：

1. 平台算子实例 ID。
2. 算子配置修订号。
3. 算子类别。
4. 输入输出契约。
5. 运行参数。
6. 当前权重 ID。
7. 权重文件地址。
8. 权重文件哈希。
9. 必要运行资源。

客户端下载这些内容并落成本地配置。

当出现以下需求时，再把快照提升为正式领域实体：

1. 历史发布版本查看。
2. 回滚。
3. 灰度发布。
4. 多个发布版本并存。
5. 审计某个客户端在某个时间点运行的精确内容。

  ↓

```

这个路径用于证明平台不要求先有场景。

  ↓

  ↓

  ↓

```

这个路径用于证明场景实例是对算子的流程组织。

### 标注工作区改造

标注工作区入口改为：

```text
算子详情
  -> 算子数据
  -> 点击图片
  -> 标注工作区
```

标注工作区顶部显示：

1. 算子名称。
2. 算子类别。
3. 当前图片。
4. 标注状态：未标注 / 已预标注 / 已确认。
5. 预标注来源。

右侧或底部显示：

1. 正式标注列表。
2. 预标注建议列表。
3. 一键应用预标注。
4. 确认为正式标注。
5. 完成并下一张。

不再显示“数据集版本正在编辑”这类旧语义。

#### 阶段二：算子详情闭环

目标：跑通算子自己的数据、标注、训练、下发。
